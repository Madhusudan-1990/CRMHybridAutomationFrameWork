PART 1 — The 30-second answer

Interviewer: "How did you use Docker and Kubernetes in your framework?"

"Two different problems, two different tools.

Docker solved determinism. The framework is Java 17, Maven, Selenium 4.31 and TestNG. Before containers, a failure could be the JDK version, the Chrome version, or a leftover chromedriver process from the previous run. I wrote a multi-stage Dockerfile — dependency layer cached, test-runner layer on top, running as a non-root user — so the same image runs on my laptop, on Jenkins and in the cluster.

Kubernetes solved the Grid. The test container does not contain a browser. It talks to a Selenium Grid 4 hub over HTTP. On the cluster the hub is a Service, the Chrome nodes are a Deployment with replicas: 2, and the test run itself is a Job — because a test suite must run once to completion and exit, not restart forever.

The piece that ties it together is a ten-line change in DriverFactory.initProp(): environment variables override the properties file. So HUB_URL=http://selenium-hub:4444/wd/hub comes from a ConfigMap, credentials come from a Secret, and not one test class or Page Object changed."
Why this version is safer than "1000 tests, 10 hours, 10 pods": your CRM repo has 14 @Test methods and thread-count="4". Anyone who opens AccountPageTest.java or testng_regression.xml can check. A story that survives cross-examination is worth more than a bigger number that does not.

2.3 The real Dockerfile — Dockerfile in this repo

This is the committed file, not a sketch:

########## STAGE 1: build the jar and cache the maven dependencies ##########
FROM maven:3.9-eclipse-temurin-17 AS build
WORKDIR /app

# copy the pom first, so the dependency layer is cached and does not rebuild on a code change
COPY pom.xml .
RUN mvn -B -q dependency:go-offline

# now copy the source and package, skipping the tests because the tests run in stage 2
COPY src ./src
RUN mvn -B -q package -DskipTests

########## STAGE 2: the test runner image ##########
FROM maven:3.9-eclipse-temurin-17
WORKDIR /app

COPY --from=build /root/.m2 /root/.m2
COPY --from=build /app/target /app/target
COPY pom.xml .
COPY src ./src

# non-root user: kubernetes refuses to run root by default under the restricted SCC
RUN useradd -m -u 10001 tester && chown -R tester:tester /app
USER tester

ENV ENV=qa \
    BROWSER=chrome \
    HEADLESS=true \
    REMOTE=true \
    CONTAINER=true \
    HUB_URL=http://selenium-hub:4444/wd/hub \
    URL=https://ui.cogmento.com/

CMD ["mvn", "-B", "test", "-Dsurefire.suiteXmlFiles=src/test/resources/testrunners/testng_regression.xml"]

Three decisions worth being able to defend

  1. COPY pom.xml . before COPY src, then mvn dependency:go-offline. Layer caching means a Java change re-uses the dependency layer. Editing one test method does not re-download the internet.
  2. Multi-stage. Stage 1 packages; stage 2 only carries the .m2 cache and the built output forward. The published image is smaller and the build stage is throwaway.
  3. USER tester on uid 10001. Kubernetes' restricted SecurityContext Constraint refuses to run a container as root. Setting a deliberate uid here is what makes the manifest in Part 5 legal — and it is a security finding in any code review to run as root.
A correction to the version of this guide you may have seen: it showed FROM openjdk:17-slim + apt-get install maven + a browser installed inside the test image. That is a weaker design and it contradicts the committed file. In this framework the test image has no browser. The browser lives in the Grid node image (selenium/node-chrome). Say that deliberately — it is the better answer, because it means you scale test capacity and browser capacity independently.

2.5 Troubleshooting: passes on laptop, fails in the container

This is the question that separates people who have actually run it. Answer it as a sequence:

# 1. Get a shell in the same image the tests run in
docker run -it --rm crm-tests:1.0 /bin/bash

# 2. Verify the environment you think you have
java -version
mvn -v
echo "$HUB_URL"

# 3. Verify the Grid is reachable FROM INSIDE the container
#    (this is where "localhost" quietly breaks everything)
curl -s http://selenium-hub:4444/wd/hub/status | head

# 4. Run a single class, not the whole regression
mvn -B test -Dtest=LoginPageTest -DfailIfNoTests=false
"The four things I check, in order: is the image the one I think it is, is the JDK inside it what the pom expects, can the container resolve the hub hostname, and does a single class fail or only the suite. Nine times out of ten it is the third — the container cannot use localhost, because localhost inside a container is the container."

PART 3 — How config gets into the container

This is the part most candidates hand-wave. You have real code, so you can be specific.

3.1 The change in DriverFactory.initProp()

Before: the properties file was the only source of truth.

After: the properties file is the default, and environment variables override it.

// DriverFactory.initProp() - after prop.load(fis)
overrideFromEnv(prop, "REMOTE");
overrideFromEnv(prop, "HUB_URL");
overrideFromEnv(prop, "CONTAINER");
// ... also BROWSER, HEADLESS, INCOGNITO, HIGHLIGHT, URL, USERNAME, PASSWORD
return prop;

private void overrideFromEnv(Properties prop, String key) {
    String value = System.getenv(key);
    if (value != null && !value.trim().isEmpty()) {
        prop.setProperty(key.replace("_", "").toLowerCase(), value.trim());  // HUB_URL -> huburl
    }
}

The environment variable name maps to the property by stripping underscores and lowercasing, so HUB_URL writes huburl, which is exactly what init_remoteDriver() already reads.

3.2 The same value, four different places, one string

Local laptop     huburl = http://localhost:4444/wd/hub      (from qa.config.properties)
Local Docker     huburl = http://host.docker.internal:4444/wd/hub   (HUB_URL env var)
docker-compose   huburl = http://selenium-hub:4444/wd/hub   (service name on the compose network)
Kubernetes       huburl = http://selenium-hub:4444/wd/hub   (Service DNS name)

Notice the last two are the same string. That is deliberate — it is why nothing in the Selenium code changes when you move from a laptop to a cluster.

3.3 The one flag Chrome needs inside a container

// OptionsManager.getChromeOptions()
if (Boolean.parseBoolean(prop.getProperty("container"))) {
    // chrome crashes with the sandbox in a container and with the default 64MB /dev/shm
    co.addArguments("--no-sandbox", "--disable-dev-shm-usage");
}

If you can explain why, you have the answer to the next question in Part 6.

PART 4 — docker-compose.yml: Grid + tests in one command

Committed in this repository, slightly shortened:

name: crm-automation
services:

  hub:
    image: selenium/hub:4.27.0
    container_name: selenium-hub
    ports:
      - "4444:4444"
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:4444/wd/hub/status"]
      interval: 10s
      retries: 12
      start_period: 20s

  chrome:
    image: selenium/node-chrome:4.27.0
    depends_on:
      hub:
        condition: service_healthy
    shm_size: 2gb
    environment:
      SE_EVENT_BUS_HOST: hub
      SE_EVENT_BUS_PUBLISH_PORT: 4444
      SE_EVENT_BUS_SUBSCRIBE_PORT: 4444
      SE_NODE_MAX_SESSIONS: "2"
    ports:
      - "7901:7900"          # live noVNC view

  tests:
    build: .
    depends_on:
      hub:
        condition: service_healthy
    environment:
      ENV: qa
      BROWSER: chrome
      REMOTE: "true"
      CONTAINER: "true"
      HUB_URL: http://selenium-hub:4444/wd/hub
      USERNAME: ${CRM_USERNAME:-}
      PASSWORD: ${CRM_PASSWORD:-}
    user: "${UID:-1000}:${GID:-1000}"
    volumes:
      - ./reports:/app/reports
      - ./screenshot:/app/screenshot
      - ./allure-results:/app/allure-results
      - ./surefire-reports:/app/target/surefire-reports

The three things in that file worth calling out

  1. condition: service_healthy — a container being started is not a Grid being ready. Without this, the node registers against a hub that is not listening yet and you get an intermittent "no slots available".
  2. shm_size: 2gb — the default container /dev/shm is 64 MB. Chrome dies with Tab crashed. This is the single most common Dockerised-Selenium failure.
  3. user: "${UID}:${GID}" — the image runs as uid 10001 for Kubernetes, but on a laptop you want the reports on your host disk to be owned by you, not by root.
export CRM_USERNAME=you@example.com CRM_PASSWORD=secret
docker compose up --build --abort-on-container-exit
docker compose logs -f tests
docker compose down -v

Open http://localhost:4444/grid/console to see the grid, and http://localhost:7901 to watch the browser live over noVNC.

5.1 The five objects, and which file holds each

Deploymentk8s/04-grid-node.yamlChrome nodes. replicas: 2 = parallel browser capacity. Includes the /dev/shm emptyDir
Jobk8s/05-test-job.yamlThe test run. Runs to completion and exits
PVCk8s/06-pvc.yamlReports outlive the pod

5.2 Deployment vs Job — the distinction interviewers test

A Deployment keeps a desired number of pods alive. If a pod finishes or dies, the Deployment creates another. That is correct for a web server or a Grid node. It is wrong for a test suite, which would restart forever and burn the cluster.

So the test run is a Job. From k8s/05-test-job.yaml:

apiVersion: batch/v1
kind: Job
metadata:
  name: crm-regression
  namespace: qa-automation
spec:
  backoffLimit: 0                # a failed suite must FAIL, not be retried 6 times
  activeDeadlineSeconds: 3600
  ttlSecondsAfterFinished: 86400
  template:
    spec:
      restartPolicy: Never
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        fsGroup: 10001           # lets the image user write into the PVC
      containers:
        - name: tests
          image: ghcr.io/madhusudan-1990/crm-tests:1.0
          envFrom:
            - configMapRef: { name: crm-framework-config }
            - secretRef:   { name: crm-framework-credentials }
          command: ["mvn"]
          args: ["-B", "test", "-Dsurefire.suiteXmlFiles=$(SUITE_XML)"]
          volumeMounts:
            - { name: reports, mountPath: /app/reports, subPath: reports }
            - { name: screenshots, mountPath: /app/screenshot }
Three details in that Job that interviewers notice
  1. backoffLimit: 0 — you want a red build, not six silent retries that eventually turn red into green.
  2. $(SUITE_XML) in args — Kubernetes expands $(VAR) in command/args from the container's own env. One manifest runs smoke or regression by changing a ConfigMap key.
  3. fsGroup: 10001 — without it the non-root image user gets Permission denied writing reports into the PVC. This is the error people hit and cannot explain.

5.3 The Chrome node — where the real pitfalls are

containers:
  - name: node-chrome
    image: selenium/node-chrome:4.27.0
    env:
      - name: SE_EVENT_BUS_HOST
        value: selenium-hub          # Service DNS, not an IP
      - name: SE_EVENT_BUS_PUBLISH_PORT
        value: "4444"
      - name: SE_EVENT_BUS_SUBSCRIBE_PORT
        value: "4444"
      - name: SE_NODE_MAX_SESSIONS
        value: "2"
    resources:
      requests: { cpu: "1", memory: 2Gi }
      limits:   { cpu: "2", memory: 4Gi }
    volumeMounts:
      - name: dshm
        mountPath: /dev/shm
volumes:
  - name: dshm
    emptyDir:
      medium: Memory
      sizeLimit: 2Gi

The emptyDir with medium: Memory at /dev/shm is the Kubernetes equivalent of shm_size: 2gb in compose. Same bug, same fix, different syntax. Being able to say that parallel is a strong signal.

5.4 Deploy and watch

docker build -t ghcr.io/madhusudan-1990/crm-tests:1.0 .
docker push ghcr.io/madhusudan-1990/crm-tests:1.0

kubectl apply -f k8s/00-namespace.yaml -f k8s/01-configmap.yaml -f k8s/06-pvc.yaml
kubectl apply -f k8s/03-grid-hub.yaml -f k8s/04-grid-node.yaml
kubectl apply -f k8s/05-test-job.yaml

kubectl -n qa-automation get pods -w
kubectl -n qa-automation logs job/crm-regression -f
kubectl -n qa-automation port-forward svc/selenium-hub 4444:4444   # grid console
A Job is immutable. kubectl apply on a modified Job is a silent no-op. Delete it first — kubectl -n qa-automation delete job crm-regression — or bump metadata.name. Candidate who know this have run it.

PART 6 — Ten questions, answered against this repo

Q1. "How did you containerise your framework?"

"Multi-stage Dockerfile. Stage 1 copies the pom, runs dependency:go-offline so the dependency layer is cached, then packages with -DskipTests. Stage 2 copies the .m2 cache and the build output forward and sets a non-root user on uid 10001. The default command is mvn test against testng_regression.xml. Critically, the image contains no browser — the browser lives in the Grid node image, so I scale test capacity and browser capacity independently."

Q2. "Why Kubernetes, not just Docker?"

"Docker made the run reproducible on one machine. Kubernetes made the Grid reproducible across a cluster. The hub is a Service with a stable DNS name, the Chrome nodes are a Deployment I can scale from 2 to 10 replicas without touching the test image, and the test run is a Job so it runs once and exits. Config and credentials come from a ConfigMap and a Secret, which means the same image is promoted from QA to Stage with a config change and a rebuild — never a rebuild for config."

Q3. "How do you handle test data in containers?"

"In this framework the Excel test data is copied into the image by COPY src ./src, which is the simple option and is correct when the data is stable and non-sensitive — it guarantees every run has identical data. For environment-specific data I would not put a binary .xlsx in a ConfigMap: ConfigMaps are UTF-8 text and Excel is not. You use a Secret with binaryData (base64) or a PVC. ConfigMaps are right for things like the suite name and timeouts, which is exactly what k8s/01-configmap.yaml does."
The original version of this guide showed a ConfigMap holding crmtestdata.xlsx with a literal block scalar. That does not work — Excel is binary and ConfigMaps are text. This corrected answer is the one that holds up.

Q4. "How do you collect reports from pods?"

"A PVC with ReadWriteMany, and the Job mounts it with a subPath per report type — reports, allure-results — so two mounts on one volume do not write into the same folder. Surefire JUnit XML goes there too, which is what Jenkins reads for the test trend graph. Screenshots go to a pod-local emptyDir because they are throwaway. When the pod is deleted the PVC keeps the reports."

Q5. "What if a container crashes mid-suite?"

"Two different answers for two different objects, and getting them backwards is a common mistake. For the Grid node, a Deployment restarts it and the hub re-registers it — that is desirable. For the test run, a Job with backoffLimit: 0 must fail, because a half-finished suite that silently restarts and re-runs is worse than a red build. I also set activeDeadlineSeconds so a hung test cannot block the pipeline forever."

Q6. "How do you run a browser in a container?"

"We deliberately do not. The test image is headless-Java-only; the browser is a separate container, selenium/node-chrome, on the Grid. The test container creates a RemoteWebDriver against HUB_URL. Two things that bite you: the node needs shm_size: 2gb in compose or an emptyDir with medium: Memory at /dev/shm in Kubernetes, or Chrome dies with Tab crashed; and Chrome needs --no-sandbox and --disable-dev-shm-usage, which I add when the container property is true."

Q7. "How do you check container health?"

"For the hub I use HTTP probes on /wd/hub/status — readiness before serving traffic, liveness with a longer initial delay. For the Chrome node, a TCP probe on 5555 is enough. For the test Job I use no probe at all, and I think that is the right call: a liveness probe that restarts a test suite mid-run turns a failed test into a passing one. The Job's exit code is the health check. What I do add is kubectl top pod and kubectl describe pod when something dies with OOMKilled."
The original guide recommended a liveness probe running pgrep -f "mvn test" on the test container. That is the wrong pattern for a batch Job — it restarts a suite that is already partly done. Probes belong on the long-running services (hub, node), not on the run.

Q8. "Test passes in Docker but fails in Kubernetes — how do you debug?"

# 1. Same image locally first — isolates "is it the image" from "is it the cluster"
docker run -it --rm ghcr.io/madhusudan-1990/crm-tests:1.0 /bin/bash

# 2. Inside the cluster
kubectl -n qa-automation exec -it job/crm-regression -- bash
kubectl -n qa-automation describe pod <pod> | grep -A 20 Environment:
kubectl -n qa-automation get pod <pod> -o jsonpath='{.status.containerStatuses[0].state}'

# 3. The four usual suspects, in order
kubectl -n qa-automation top pod                  # CPU / memory  -> OOMKilled?
kubectl -n qa-automation logs job/crm-regression   # did HUB_URL arrive?
kubectl -n qa-automation get pvc                  # is the volume bound?
kubectl -n qa-automation get endpoints selenium-hub   # did the nodes register?

Q9. "What about Secrets and ConfigMaps?"

"ConfigMap for non-sensitive config, Secret for credentials, and in this framework both arrive as environment variables via envFrom, which initProp() then lets override the properties file. One thing I am deliberate about: the real k8s/02-secret.yaml is in .gitignore. Only the example template is committed. In Jenkins the credentials come from the Credentials Store inside a withCredentials block, never from a file. Secrets are base64, which is encoding not encryption, so I also scope them to a namespace and avoid stringData with real values in any committed file."

Q10. "What did it actually improve?"

"Three measurable things. Environment-related failures dropped by about 60% — those were the failures where the test was fine and the machine was not. Pipeline stability sat at roughly 95% for the regression stage, because a broken agent no longer broke the run. And onboarding a new engineer went from setting up JDK, Maven, Chrome and drivers to docker compose up. The honest caveat I always give: containerising does not make a flaky test reliable. It removes the environment as a variable, so that when something is flaky you can finally trust that it is the test."

PART 7 — Mistakes to avoid

#WrongRight
1 Rebuilding the image on every run Build once, run many. Layer caching is the whole point of copying the pom first
2 ENV DB_PASSWORD=... in the Dockerfile Secret / Credentials Store. Values are ${VAR} at runtime, never baked into a layer — an image is a public artifact once pushed
3 No resource requests/limits on the Grid node One runaway Chrome node starves the node. Set both, and expect OOMKilled when you get the limit wrong
4 Running the test suite as a Deployment It is a Job. A Deployment restarts finished pods forever
5 A liveness probe on the test Job that restarts mvn Probes on the hub and node only. The Job's exit code is the signal
6 shm_size left at the default 64 MB 2 GB in compose, emptyDir medium: Memory in Kubernetes. Chrome will otherwise die with Tab crashed
7 Committing 02-secret.yaml Gitignore the real file, commit only the .example template
8 Binary .xlsx in a ConfigMap ConfigMaps are UTF-8 text. Use binaryData or a PVC for Excel
9 kubectl apply to change an existing Job Jobs are immutable — delete it first, or rename it
10 Running the container as root Non-root uid, and fsGroup set so that uid can write to the PVC

PART 9 — Your answers

One minute

"I containerised the CRM automation framework with Docker to remove environment drift — same JDK, same Maven, same image on my laptop, Jenkins and the cluster. The image has no browser in it; the browser is a separate Selenium Grid node container, so I scale test capacity and browser capacity independently. On Kubernetes the hub is a Service, the Chrome nodes are a Deployment, and the test run is a Job. The only Java change was a ten-line override in DriverFactory.initProp() so environment variables beat the properties file — which is how the same image runs in four places with four different huburl values and zero code changes between them."

Five minutes — the flow, in order

  1. Build. Multi-stage Dockerfile. Pom copied first for layer caching. Tests skipped in the build stage because they run in the runner stage.
  2. Local parity. A developer runs docker compose up and gets the exact Grid and the exact runner CI uses. http://localhost:7901 shows the browser over noVNC.
  3. CI. Jenkinsfile_docker: build image, start the Grid and wait for the hub healthcheck, run the tests container, publish JUnit + Extent + Allure, push the image, trigger the Kubernetes Job, and docker compose down -v in post.
  4. Cluster. ConfigMap supplies HUB_URL and SUITE_XML, Secret supplies credentials, the Job runs as uid 10001 with fsGroup so it can write to the PVC, and backoffLimit: 0 means a failed suite is a failed build.
  5. Scale. Browser capacity is replicas on the node Deployment. Suite selection is one ConfigMap key, because $(SUITE_XML) expands in the Job's args.

Closing line

"Containerisation did not make our tests faster. It made them trustworthy. We went from 'is the test flaky or is the machine broken?' to 'the test is flaky', because the environment stopped being a variable. That is the actual ROI."

Practice these

  1. Why not just run the suite in parallel on Jenkins without Docker?
  2. Deployment or Job for a test run — and why does it matter?
  3. What breaks when /dev/shm is left at 64 MB?
  4. How do you keep credentials out of a Docker image layer?
  5. Why can the container not use localhost to reach the hub?
  6. What is the difference between backoffLimit: 0 and 3?
  7. How would you run smoke instead of regression without rebuilding the image?
  8. Where do reports survive after the test pod is deleted?

Do / Don't

DO — name the actual files; admit the honest numbers; explain why a choice was made; say what you would still improve (the plaintext credentials in qa.config.properties are the known backlog item).

DON'T — say "Docker is like a VM"; claim 1000 tests when the repo shows 14; use a Deployment for a test run; claim perfect reliability.
